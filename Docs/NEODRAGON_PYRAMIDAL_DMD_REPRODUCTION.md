# NeoDragon Pyramidal-DMD Reproduction: Design, Fidelity Audit, and 10k Result

## Status at a Glance

This document records the first practical attempt to reproduce the Pyramidal
Distribution Matching Distillation (DMD) stage of
[NeoDragon](https://arxiv.org/html/2511.06055v1). It is deliberately separate
from Mobile-OV bridge, DreamLite image-bridge, OpenVid flow-matching, OPSD,
and full-DiT fine-tuning experiments.

The question is narrow:

> Can the released NeoDragon multi-step video DiT train a new one-step,
> `1-1-1` Pyramidal video DiT using the public Pyramidal-DMD description?

The first real run was executable and numerically stable for 10,000 updates,
but it used an incorrect six-unit target topology. Its motion result is
therefore a useful diagnostic, not a verdict on paper-aligned DMD.

## V2 Protocol Correction

The original 10k run in this document is retained as a **historical
diagnostic**, not as a valid quality verdict on Pyramidal DMD. Its trainer
treated latent unit zero as an external SSD1B anchor and trained only units
`1..6`. That assumption contradicted the actual synthetic data: it was
generated with `image=None`, so all seven units are native multi-step T2V
outputs. It also contradicts the paper's step-distillation setting, which
generates a complete seven-unit video with the same `1-1-1` schedule.

`train_neodragon_pyramidal_dmd.py` now defaults to **DMD-v2**:

```text
all native units:  unit 0..6 x Pyramidal stage 0..2 = 21 one-step calls
teacher CFG:       unit 0 = 7.0; units 1..6 = 5.0
student/fake:      conditional-only one-step calls
```

The correction reuses the existing 187,955 teacher trajectories; no expensive
trajectory regeneration is needed. The old six-unit path is available only as
an explicit legacy ablation and cannot be resumed into the all-unit protocol.
An H200 Slurm smoke ran all 21 positions and verified the saved schedule and
checkpoint history before the real job was exposed.

This is still useful progress. It separates three questions that were
previously mixed together:

1. The DMD code path and distributed training loop work end to end.
2. The existing Exp1 Mobile-OV video bridge is functionally compatible with a
   DMD student when the native conditioning contract is kept fixed.
3. The unresolved problem is the **quality of the DMD student rollout**, not
   simple text-condition compatibility.

## Scope and Terms

This work is deliberately separate from every previous Mobile-OV bridge,
OpenVid flow-matching, OPSD, and image-conditioning experiment. Its name in
code, checkpoints, and Slurm jobs is **NeoDragon Pyramidal-DMD Reproduction**.
It targets one question only:

> Can the released multi-step NeoDragon DiT supervise a new conditional
> one-step 1-1-1 video DiT through the Pyramidal Distribution Matching
> Distillation procedure described in the NeoDragon paper?

For the synthetic native-T2V DMD task, the first latent is a **trainable native
unit**, not an external image anchor. Each of the seven units has three
Pyramidal stages, so the corrected student has exactly
`7 x 3 x 1 = 21` conditional DiT calls. An SSD1B/DreamLite first-frame
integration is a separate deployment protocol and must not silently redefine
the native DMD training targets.

| Term | Meaning in this work |
| --- | --- |
| Multi-step teacher | Released `diffusion_transformer_320p_multistep_t2v` DiT. It is the released step-distillation source and is already the pruned 18-block architecture, not the original unpruned 24-block model. |
| DMD student | A trainable copy of the released multi-step DiT that learns one Euler update per Pyramidal stage. |
| Fake model | A second trainable copy that estimates the flow of the *current student endpoint distribution*. It is not used at inference. |
| Hybrid control | Released NeoDragon `1-1-1` model. It is the practical quality baseline, but it is not the frozen DMD teacher. |
| Native unit zero | The first latent generated by the multi-step T2V teacher when `image=None`; DMD-v2 trains it directly with no causal history. |
| External first-frame anchor | A latent supplied by SSD1B/DreamLite at deployment. It is not present in the DMD-v2 teacher trajectories. |

## What Is Implemented

The pipeline has three explicit stages:

1. **Synthetic teacher data**: `prepare_neodragon_dmd_synthetic_data.py` takes
   prompts only. It uses the released native multi-step model at `20/10` steps
   with native CFG and writes seven native latent units per prompt. Raw OpenVid
   pixels or VAE latents are not used as the DMD target distribution.
2. **Pyramidal DMD training**: `train_neodragon_pyramidal_dmd.py` loads three
   copies of the released multi-step DiT. The frozen copy is the teacher. The
   student and fake model both initialize from the same multi-step checkpoint.
   No Mobile-OV bridge is loaded or optimized.
3. **Controlled student rollout**: `evaluate_neodragon_pyramidal_dmd.py` and
   `audit_neodragon_dmd_inference_contract.py` audit the one-step call
   contract. For DMD-v2, the reference protocol is a full native seven-unit
   rollout; an externally anchored rollout remains a separately labelled
   deployment test.

The primary implementation files are:

- `new_mobile_ov/training/neodragon_pyramidal_dmd.py`
- `tools/prepare_neodragon_dmd_synthetic_data.py`
- `tools/train_neodragon_pyramidal_dmd.py`
- `tools/evaluate_neodragon_pyramidal_dmd.py`
- `tools/audit_neodragon_dmd_inference_contract.py`
- `scripts/prepare_neodragon_pyramidal_dmd_synthetic_1node8gpu.sbatch`
- `scripts/reproduce_neodragon_pyramidal_dmd_1node8gpu.sbatch` (legacy v1)
- `scripts/reproduce_neodragon_pyramidal_dmd_v2_1node8gpu.sbatch` (corrected)
- `scripts/audit_neodragon_pyramidal_dmd_v2_native_1node1gpu.sbatch`
- `scripts/finalize_neodragon_pyramidal_dmd_subset_1node1gpu.sbatch`

At every update, all DDP ranks select the same position from the native
`7 units x 3 stages` grid. This prevents ranks from taking different causal
DiT branches:

```text
1. Load [unit_0, ..., unit_6] from a synthetic teacher trajectory.
2. Choose one native unit and one Pyramidal stage.
3. Build the stage start/end pair around that teacher endpoint.
4. Run two fake updates on detached current student endpoints.
5. Run the one-step student from the stage start.
6. Re-noise the predicted endpoint at a fixed local tau.
7. Compare frozen teacher flow and frozen fake flow at that same probe.
8. Back-propagate DMD surrogate + Cauchy endpoint stabilizer.
```

## Why DMD Is Needed

The released multi-step DiT can generate high-quality Pyramidal video but needs
multiple neural function evaluations per stage. The released Hybrid model is
fast because it runs a specialised one-step `1-1-1` schedule. A naive
endpoint-MSE distillation can make a one-step student predict an average-looking
endpoint, which often loses sharp detail and motion diversity.

DMD instead tries to match the *student's generated distribution* to the
teacher distribution. The fake model answers: "what flow does the current
student distribution have at this noisy point?" The frozen teacher answers:
"what flow should a high-quality conditional distribution have at the same
point?" Their difference supplies the direction that updates the student.

```text
prompt + causal latent history
             |
             v
    frozen multi-step teacher (with CFG) ----> desired local flow
             |
student endpoint --> re-noise at local tau --> fake model ----> current flow
             |                                      |
             +------ teacher flow - fake flow -------+
                                |
                                v
                    update one-step student only
```

The fake model is needed because the student distribution changes after every
student update. A frozen fake would model an old student distribution and would
no longer provide the correct DMD direction.

## What Is Explicitly Paper-Aligned

The following items are directly supported by Section 3.4, "Pyramidal DMD," of
the [NeoDragon paper](https://arxiv.org/html/2511.06055v1#S3.SS4). The paper
explicitly describes the teacher, one-step student, fake model, inverse
teacher-flow-error weighting, Cauchy endpoint term, and alternating updates.

| Paper item | Current implementation |
| --- | --- |
| Stage-wise Pyramidal start/end distributions | Implemented in `build_stage_pair()` using released scheduler endpoints and shared stage noise. |
| Student, fake, and frozen teacher | Three DiT copies. Student and fake initialize from the released multi-step checkpoint. |
| Fake Flow Matching on detached student endpoints | Implemented with the start-to-end stage flow of the detached current student endpoint. |
| Teacher-minus-fake DMD direction | Implemented through a surrogate scalar whose gradient with respect to the student endpoint is the DMD direction. |
| Inverse L1 teacher-error sample weight | Implemented with a numerical denominator floor and an explicit maximum weight cap. |
| Cauchy endpoint term, weight `0.5` | Implemented as `log(1 + ||student_endpoint - teacher_endpoint||^2)`. |
| One student update per two fake updates | Implemented as `student:fake = 1:2`. |
| Four fixed student local noise values | Implemented as `0.125, 0.375, 0.625, 0.875`. |
| Uniform fake local noise | Implemented as `tau ~ Uniform(0, 1)`. |
| Guided teacher prediction | DMD-v2 uses released first-unit CFG `7.0` for unit zero and video CFG `5.0` for units one through six; student and fake are conditional-only. |
| Lower-resolution DMD checkpoint | Implemented with the released 320p multi-step checkpoint, consistent with the paper's stated lower-resolution choice after target-resolution instability. |

The paper reports **5,000 DMD iterations on 16 H100 GPUs**. It does not publish
the DMD batch size, prompt set, optimizer details, or all data-loader choices.
Therefore an iteration count alone is not a comparable training budget.

## Training Mechanics

For a clean teacher endpoint `z`, stage `i` has released scheduler endpoints
`sigma_start[i]` and `sigma_end[i]`. The trainer constructs the Pyramidal
stage endpoints with the same noise sample `epsilon`:

```text
y_start = (1 - sigma_start) * Up(Down(z, 2), 2) + sigma_start * epsilon
y_end   = (1 - sigma_end)   * z                    + sigma_end * epsilon
```

At stage zero, `Up(Down(z))` is replaced by zero, so the stage starts from
pure noise. The one-step student predicts a velocity from `y_start`, then its
endpoint is the release scheduler's one Euler update:

```text
z_student = y_start - D_student(y_start, t_start)
```

The student itself is conditional-only: it makes one DiT call at deployment.
The frozen multi-step teacher uses native first-unit CFG `7.0` for unit zero
and video CFG `5.0` for units one through six to transfer the teacher's guided
distribution into conditional one-step calls. Unit zero has an empty causal
history; later units receive the preceding native teacher units during
training.

For a local stage noise `tau`, the endpoint is re-noised:

```text
z_tau = (1 - tau) * y_end(z_student) + tau * y_start(z_student)
```

The fake model learns ordinary Pyramidal Flow Matching on this **detached
current student endpoint distribution**:

```text
L_fake = MSE(D_fake(z_tau, tau), y_start(z_student) - y_end(z_student))
```

The fake optimizer runs twice per student update, matching the paper's `1:2`
student:fake ratio. The student receives the Distribution Matching direction
from the difference between frozen teacher and fake velocities. The scalar
surrogate is only a mechanism to inject this gradient, so it is logged as
`dmd_surrogate` and must not be interpreted as an ordinary decreasing loss.

```text
g_DMD = w * (D_teacher(z_tau, tau) - D_fake(z_tau, tau))
w     = clamp(1 / L1(D_teacher, y_start - y_end))
```

The supervised endpoint stabilizer is the Cauchy term described in the paper:

```text
L_cauchy = log(1 + ||z_student - z||_2^2)
L_student = 1.0 * L_DMD + 0.5 * L_cauchy
```

Student `tau` cycles through four fixed values: `0.125`, `0.375`, `0.625`, and
`0.875`. Fake `tau` is sampled uniformly in `[0, 1]`. Every rank cycles the
same seven-unit by three-stage schedule, preventing DDP ranks from taking
different DiT branches.

## What Was Chosen by Us, Not Confirmed by the Paper

The code follows the public DMD mechanism, but the following details are
implementation choices rather than verified paper hyperparameters.

| Choice | Current implementation | Why it was chosen | Remaining uncertainty |
| --- | --- | --- | --- |
| Prompt corpus | Deterministic OpenVid recaption sample | Already available, diverse, and inexpensive for teacher synthesis | The paper does not release its DMD prompt set or filtering recipe. |
| Dataset size | 187,955 ready trajectories out of 350,000 requested | Uses all valid work after the 72-hour teacher job reached walltime | Coverage may be insufficient for one-step video dynamics. |
| Hardware and batch | 8 H200 GPUs, batch 1/GPU, global batch 8 | Fits three approximately 1.5B DiTs plus optimizer state | The paper uses 16 H100 GPUs, but does not publish its batch size. |
| Training length | 10,000 updates | Twice the paper's reported 5,000 updates to obtain an initial signal | More steps cannot fix an objective or rollout mismatch. |
| Optimizer | AdamW, `1e-6` for student and fake | Conservative full-DiT starting point | Exact paper optimizer and schedule are not public. |
| Inverse-error cap | Weight capped at `100` | Avoids numerical explosions when teacher error is nearly zero | Changes the effect of rare large-gradient samples. |
| History at training | Clean native teacher units provide prior-unit history | Stable stage-local training from stored trajectories | Deployment uses prior student units; the paper does not state its teacher-forced versus rollout-history policy. |
| External-anchor integration | Not included in DMD-v2 | The synthetic teacher is native T2V (`image=None`) | A later deployment audit must separately test SSD1B/DreamLite anchors. |
| Text/context stack | Frozen released multi-step text encoder and context adapter | Keeps the teacher/student condition contract fixed | A future monolithic fine-tune must preserve this contract or re-distill the bridge. |

### Euler-Scaling Compatibility Gap

The paper writes the one-step student endpoint with an explicit factor
proportional to `sigma / (sigma_start - sigma_end)`. The current
implementation uses the released scheduler convention:

```python
student_endpoint = stage_start - student_predicted_flow
```

This was chosen because the released scheduler uses a one-Euler-step
`start - flow` update at its stage start. A direct local H200 ablation applied
the paper's printed scale factor literally to release-model outputs: it raised
motion energy but collapsed spatial detail (Laplacian sharpness approximately
`5` versus approximately `429` for the multi-step reference). Therefore DMD-v2
preserves the release scheduler representation rather than inserting a scale
factor whose coordinate system has not been established. This remains a
reproduction uncertainty, but a naive equation-level transplant is now known
to be harmful.

### Dataset and Anchor Status

The intended synthetic dataset contained 350,000 prompt-conditioned teacher
trajectories. It was generated from a deterministic sample of
`download_data/data/openvid/manifests/openvid_all_recaptions_merged.csv`, not
from raw video pixels. This is deliberate: DMD targets the teacher-generated
latent distribution, not OpenVid ground-truth VAE latents.

| Field | Value |
| --- | --- |
| Teacher | Released 320p multi-step NeoDragon DiT |
| Resolution | `320 x 512` |
| Video length | 49 frames, seven latent units |
| First unit | 20 steps per Pyramidal stage, CFG `7.0` |
| Six video units | 10 steps per Pyramidal stage, video CFG `5.0` |
| Prompt source | OpenVid merged recaptions |
| Sampling seed | `20260812`, deterministic per prompt index |
| Ready trajectories | 187,955 |

The teacher-data job reached walltime before all 350,000 samples completed.
The partial dataset was finalized safely from atomically written payloads:

```text
data/neodragon_pyramidal_dmd_320p/manifest_partial.csv
data/neodragon_pyramidal_dmd_320p/metadata_partial.json
```

The metadata marks the dataset as `partial`. It is adequate for the first
DMD test, but it is not evidence that the paper's data scale or prompt
distribution has been reproduced.

These differences are explicit so a positive or negative result is not
mistaken for a direct comparison with the paper's unpublished data and
lower-resolution teacher.

## Berzelius Commands

Run from the repository root. The synthetic-data job resumes at individual
latent files, so resubmitting after the 72-hour walltime is safe. The manifest
is written after all requested samples have completed.

```bash

MAX_PROMPTS=350000 sbatch scripts/prepare_neodragon_pyramidal_dmd_synthetic_1node8gpu.sbatch

# 2. Finalize a valid manifest if the long teacher-data job ended early.
sbatch scripts/finalize_neodragon_pyramidal_dmd_subset_1node1gpu.sbatch

# 3. Train DMD-v2 on the completed partial set. It deliberately refuses a
# legacy v1 resume because the unit protocol is different.
MANIFEST=data/neodragon_pyramidal_dmd_320p/manifest_partial.csv \
RUN_NAME=dmd_repro_v2_all7_10k \
STEPS=10000 \
SAVE_EVERY=500 \
ARCHIVE_EVERY=5000 \
sbatch scripts/reproduce_neodragon_pyramidal_dmd_v2_1node8gpu.sbatch

# 4. Audit native full-video one-step inference before an external-anchor test.
CHECKPOINT=output/neodragon_pyramidal_dmd_reproduction/dmd_repro_v2_all7_10k/neodragon_pyramidal_dmd_student_step010000.pt \
RUN_NAME=dmd_v2_native_10k_audit \
sbatch scripts/audit_neodragon_pyramidal_dmd_v2_native_1node1gpu.sbatch
```

For a small end-to-end DDP validation before the full data run:

```bash
sbatch scripts/smoke_reproduce_neodragon_pyramidal_dmd_2gpu.sbatch
```

The DMD-v2 job defaults are global batch `8`, student learning rate `1e-6`,
fake learning rate `1e-6`, `1:2` student:fake updates, and `10,000` training
steps. The paper reports 5,000 iterations, but DMD-v2 has 21 native
unit/stage positions and our global batch is only eight; 10k is a conservative
empirical budget rather than a claim of paper-scale equivalence. The resume
state is intentionally much larger than the deployable student checkpoint
because it contains the student, fake model, both optimizer states, and
training history.

## Metrics and Decision Criteria

The trainer writes `history.json` with the following values:

- `endpoint_mse`: supervised error from student endpoint to the teacher
  synthetic endpoint. It should remain finite and generally decrease, but it
  is not sufficient to prove distribution matching.
- `cauchy`: stabilizing endpoint term. This should remain finite; a collapse to
  near zero while rollout quality fails is a warning that this term dominates.
- `fake_mse`: Pyramidal Flow Matching error of the fake model. It should not
  diverge and should track the current student distribution.
- `teacher_pf_error`: frozen teacher error on the re-noised student endpoint.
  This checks that DMD probes remain in a region where the teacher provides a
  meaningful flow direction.
- `direction_rms` and `mean_sample_weight`: DMD gradient-health diagnostics.
  A near-zero direction for the whole run means the distribution term is not
  contributing; runaway weights indicate an unstable inverse-error region.
- `dmd_surrogate`: do not compare this as a conventional loss. Its sign and
  magnitude depend on the gradient-injection construction.

The first quality gate is the controlled evaluator: it must execute all 21
student calls, produce finite `[B,16,7,40,64]` latents, and beat a randomly
initialized student on held-out synthetic teacher samples. The second gate is
visual/video evaluation with a fixed first-frame protocol. Only after these
two gates should the student be considered for a full first-frame integration
or mobile pipeline benchmark.

## Historical v1 External-Anchor Visual Result

The final v1 checkpoint was evaluated with the same released SSD1B first-frame
pipeline for both models. The v1 DMD student replaced only the six video-unit
calls; the released Hybrid baseline used the same initial anchor and the same
noise-seed protocol. This is **not** the native full-video protocol used by
DMD-v2, so it must not be used to select or reject the corrected run.

Three prompts were tested: astronaut, driving car, and waterfall. The local
comparison sheet and metrics are stored under:

```text
output/neodragon_pyramidal_dmd_inference_local/dmd10k_3prompt/
  comparison_sheet_all.png
  temporal_metrics.json
```

The DMD videos are valid and recognisable, and individual frames can look
sharp. However, the released Hybrid control has visibly stronger camera and
subject motion. The DMD student tends to preserve a nearly static scene.
Sharper individual frames must not be read as higher video quality when the
temporal dynamics are missing.

The following diagnostics are descriptive measurements, not VBench or human
preference scores:

| Prompt | Model | Mean frame-to-frame MAE | Optical-flow magnitude | Laplacian sharpness |
| --- | --- | ---: | ---: | ---: |
| Astronaut | DMD 10k | 0.00171 | 0.0564 | 113.53 |
| Astronaut | Released Hybrid | 0.00804 | 0.4784 | 82.48 |
| Driving car | DMD 10k | 0.00402 | 0.1334 | 136.46 |
| Driving car | Released Hybrid | 0.01096 | 0.4755 | 118.65 |
| Waterfall | DMD 10k | 0.00199 | 0.0719 | 278.40 |
| Waterfall | Released Hybrid | 0.00691 | 0.2937 | 194.05 |

Across these prompts, the DMD student has optical-flow magnitude about
`0.087` versus `0.416` for released Hybrid, or roughly 21% of the control's
measured motion. DMD rollout time was `1.71s` versus `1.70s` for released
Hybrid after model loading. This is expected because both use the same
`1-1-1` schedule; this experiment targets quality recovery, not further
speedup of an already one-step pipeline.

## Historical v1 Bridge Compatibility Audit

An additional audit tested whether the successful Exp1 64k Mobile-OV video
bridge can condition the v1 10k DMD student. It used three prompts, a real
SSD1B anchor, and the 18 legacy video-stage calls. It compared the same
DMD-native state under native multi-step condition, released Hybrid native
condition, and SmolVLM2 plus the Exp1 bridge.

| Comparison | Token cosine | Token relative L2 | DiT-flow cosine | DiT-flow relative L2 |
| --- | ---: | ---: | ---: | ---: |
| Hybrid native vs multi-step native | 0.9980 | 0.0627 | 0.99998 | 0.00631 |
| Exp1 bridge vs multi-step native | 0.6471 | 0.9368 | 0.99964 | 0.02511 |
| DMD multi-step condition vs released Hybrid response | - | - | 0.99544 | 0.09169 |

The bridge embeddings are not close under raw cosine or L2 distance, but the
frozen DMD DiT response is almost identical to the native response. This
confirms the main Exp1 lesson: **raw embedding similarity is not the correct
bridge success criterion.** The meaningful contract is whether the frozen DiT
reacts equivalently.

Released Hybrid and multi-step native conditions are also highly compatible.
Therefore, if future monolithic fine-tuning keeps the text encoder and
context-adapter output contract fixed, the existing Exp1 bridge is likely
reusable. If that contract changes, the bridge must be re-distilled against
the new frozen DiT.

This audit does not prove that the DMD student is good. Its response still
differs from released Hybrid by `0.0917` relative L2 at one deployed state,
and this can compound over 18 causal calls. The visual result confirms that
the rollout gap is currently substantial.

## What the 10k Result Does and Does Not Tell Us

### Supported Conclusions

1. The distributed implementation, fake-model updates, checkpointing, and the
   legacy 18-call external-anchor topology run successfully.
2. The synthetic trajectory dataset is valid enough to train for 10k updates
   without numerical collapse.
3. The current DMD student can generate coherent videos from a real SSD1B
   anchor, so the integration boundary is technically viable.
4. The Exp1 64k bridge can control the DMD student's frozen DiT response even
   though its raw hidden embeddings differ strongly from native embeddings.
5. The v1 bottleneck is the distilled video-DiT rollout, especially motion,
   rather than a simple bridge-condition mismatch.

### Unsupported Conclusions

1. The v1 run does **not** demonstrate numerical reproduction of the paper's
   DMD result or its reported VBench quality because it omitted native unit
   zero.
2. It does **not** establish that 10k updates are sufficient. The paper's 5k
   update count cannot be scaled without its missing batch and data details.
3. It does **not** show that adding more OpenVid prompts alone will solve the
   weak-motion result.
4. It does **not** validate an SSD1B-anchor deployment distribution during
   DMD training; DMD-v2 instead tests the native full-video objective first.
5. It does **not** justify monolithic fine-tuning followed by DMD until the
   corrected core reproduction recovers released Hybrid behavior more closely.

## Priority Checks Before Scaling Further

1. **Run and audit DMD-v2 first.** It is the minimum corrected native-T2V
   protocol. Compare its full seven-unit rollout against both the released
   multi-step teacher and released Hybrid with identical native prompts/seeds.
2. **Measure teacher-forced versus generated-history exposure.** The current
   trainer sees clean teacher history while deployment sees prior student
   generations. A small controlled comparison should establish how much this
   autoregressive mismatch suppresses motion.
3. **Test an external anchor only after the native gate.** A separate
   SSD1B/DreamLite experiment can then measure anchor-distribution transfer
   without confusing it with core DMD fidelity.
4. **Increase scale only after the above checks.** Global batch 8 may give the
   fake model too little distribution coverage, but more compute cannot repair
   an unverified rollout protocol or history mismatch.
5. **Select with visual and benchmark gates.** A decreasing Cauchy term or
   endpoint MSE must not select a checkpoint. Every candidate needs
   same-anchor video comparisons and a semantic/motion benchmark.

## Final Conclusion

This DMD effort has crossed the first engineering gate: it is a real,
distributed, stage-wise DMD implementation rather than a conceptual sketch.
The v1 10k checkpoint is not, however, a valid quality result because its
target topology was wrong. DMD-v2 corrects the confirmed error without new
teacher data and preserves the released scheduler representation that the
runtime expects.

The next decision must be driven by DMD-v2's same-prompt, full-native rollout
against the multi-step teacher and released Hybrid. Only after that quality
gate should external-anchor transfer, larger batch size, or monolithic
fine-tuning be considered.
